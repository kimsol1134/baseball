# iOS 유료 게임 상위권 목표 개선 계획

| 항목 | 값 |
|---|---|
| 문서 ID | DOC-IOS-TOP |
| 버전 | 1.0 |
| 기준일 | 2026-07-25 |
| 목표 | App Store **유료 게임 차트 5위권** |
| 선행 문서 | DOC-IOS-PAID(유료앱 전환), DOC-19(비주얼 디렉션), ADR-005/006/007(코어 공정성 경계) |
| 수익 모델 | **유료앱 단일 확정.** 무료 고교 + 프로 IAP 구조로 되돌리지 않는다 |

## 0. 이 문서가 다루는 것

DOC-IOS-PAID는 "환불당할 앱"을 "정상 작동하는 앱"으로 만들었다. 그건 출발선이다.
이 문서는 출발선에서 **유료 차트 5위권**까지의 격차를 다룬다.

측정된 현실:

| 항목 | 현재 |
|---|---|
| 저장소 전체 오디오 파일 | **0개** |
| GameKit / 업적 / 리더보드 | **0개** |
| 코어의 타격 조작 로직 | **0줄** (투수 전용 게임) |
| iOS에 이식된 게임 모드 | 프로 커리어 1개 (고교 커리어·피처랩 미이식) |
| 프로 커리어 루프 | 12시즌 × 24주, **매주 같은 카드 5장 중 택1** |
| 투구 조작 | 드롭다운 4개 + 버튼 1개 |

## 1. 왜 이 네 가지인가

유료 게임은 **첫 30초의 촉감**과 **3주차의 재접속 이유**로 팔린다. 위 표에서 그 두 가지에
직접 닿는 항목만 골랐다.

| # | 작업 | 무엇을 고치는가 | 투입 대비 |
|---|---|---|---|
| S | 사운드 | "진짜 게임인가"의 1차 판정. 야구는 소리의 스포츠다 | 최고 |
| D | 투구 손맛 | 코어 루프가 설문 제출이 아니게 됨 | 높음 (코어 변경) |
| H | 고교 커리어 이식 | 콘텐츠 총량 3배. **코어는 이미 완성돼 있음** | 최고 |
| R | 리텐션 | 3주차에 다시 켤 이유 | 높음 |

**범위 밖으로 남기는 것**: 타격 조작. 코어에 타격 로직이 없어 새 시뮬레이션 축을 만들어야
하고, 그건 이 네 가지를 전부 끝낸 뒤 판단할 별도 프로젝트다. 지금 손대면 넷 다 반쯤 된다.

## 2. S — 절차 합성 오디오

### 2.1 왜 녹음 샘플이 아닌가

저장소에 오디오 에셋이 하나도 없고, 라이선스가 확인된 음원을 확보할 경로가 이 작업 안에
없다. 출처 불명 샘플을 넣는 것은 App Store 심사와 법무 양쪽에서 위험하다.

대신 **런타임 절차 합성**을 쓴다.

- 용량 0. 앱 크기에 영향이 없다.
- 게임 상태에 반응한다. 타구 속도 → 타격음 세기, 레버리지 → 관중 밀도.
- 나중에 녹음 샘플을 확보하면 `GameAudioCue` 뒤편만 바꾸면 된다. 호출부는 그대로다.

### 2.2 설계

`apps/ios/Sources/GameAudio.swift`

```
AVAudioEngine
 ├── crowdNode  (AVAudioSourceNode)  — 지속 관중 베드, 레버리지로 볼륨 제어
 └── cueNode    (AVAudioSourceNode)  — 단발 효과음 믹스 버스
```

효과음은 세 가지 프리미티브의 조합으로 만든다.

| 프리미티브 | 소리 |
|---|---|
| 필터된 노이즈 버스트 | 미트 포구, 배트 타격, 관중 웅성거림 |
| 감쇠 사인/삼각 | 심판 콜, 성장 신호, UI 탭 |
| 두 소스의 엔벨로프 합 | 홈런(타격 + 환호), 삼진(미트 + 환호) |

큐 목록:

| 큐 | 쓰이는 곳 |
|---|---|
| `pitchRelease` | 던지기 순간 |
| `gloveCatch` | 볼·루킹 스트라이크 |
| `swingMiss` | 헛스윙 |
| `batContact` / `batFoul` | 인플레이 / 파울. 타구 속도로 세기 조절 |
| `umpireStrike` / `umpireBall` | 카운트 변화 |
| `crowdCheer` / `crowdGroan` | 삼진·아웃 / 피안타·실점 |
| `growth` / `milestone` | 능력 상승 / 주요 기록 |
| `uiSelect` | 선택 카드·존 그리드 탭 |

### 2.3 시스템 예절 (심사 품질에 직결)

- `AVAudioSession` 카테고리 `.ambient` + `.mixWithOthers`. **사용자가 듣던 음악을 끊지 않는다.**
- 무음 스위치를 존중한다(`.ambient`의 기본 동작).
- 백그라운드 진입 시 엔진 정지, 복귀 시 재개.
- 설정에서 소리·햅틱을 각각 끌 수 있고 값은 저장된다.

## 3. D — 투구 조작에 손맛

### 3.1 문제

지금은 구종/코스/노림/힘 배분을 고르고 버튼을 누른다. **결정은 있는데 신체적 표현이 없다.**
같은 선택을 한 두 사람의 결과가 같다. 플레이어가 "내가 잘 던졌다"고 느낄 여지가 없다.

### 3.2 코어 변경 — 결정론과 골든 픽스처를 지키면서

`packages/simulation-core`에 입력 축을 하나 추가한다.

```swift
public struct PitchDelivery: Codable, Equatable, Sendable {
    /// 릴리스 타이밍 정확도 0–1000. 500이 중립.
    public let releaseAccuracy: Int
    /// 조준 안정도 0–1000. 500이 중립.
    public let aimAccuracy: Int
}
```

`SubmitPitchParams.delivery: PitchDelivery?` — **옵셔널**이다.

지켜야 할 규칙(memory: `baseball-determinism-fixture-rules`):

1. **`delivery == nil`이면 기존 동작과 바이트 단위로 동일해야 한다.** 데스크톱·RPC·골든
   픽스처가 전부 이 경로를 탄다.
2. **새 RNG 뽑기를 추가하지 않는다.** 보정은 순수 가산이다. 핸디드니스 플래툰이 쓴 것과
   같은 패턴이다.
3. **중립값(500/500)은 0 보정을 낸다.** 그래야 "입력 없음"과 "완벽히 평범한 입력"이 같다.
4. `eventHash`에는 `delivery`가 있을 때만 항목을 더한다. 없으면 해시가 그대로다.

적용 지점은 `executePitch`의 `executionQuality` 한 곳이다. 물리 판정이나 타자 계획에는
손대지 않는다. ADR-005의 "상황은 의도를 바꿀 수 있어도 실행·판정은 상황을 모른다" 경계를
그대로 둔다 — 플레이어 입력은 *실행 품질*이지 판정이 아니다.

보정 범위는 ±120 / 1000 으로 묶는다. 능력치가 만드는 차이보다 작게 두어, 조작이 능력을
대체하지 않고 **능력 위에 얹히게** 한다.

### 3.3 조작 설계

```
  ┌─────────────────────────┐
  │      스트라이크존        │   ← 손가락을 끌면 조준 크로스헤어가 따라온다
  │     ┌───┬───┬───┐       │      (고른 존 칸 안에서만 움직임)
  │     │   │ ✛ │   │       │
  │     └───┴───┴───┘       │
  └─────────────────────────┘
  ┌─────────────────────────┐
  │ ▓▓▓▓▓▓▓░░░│░░░░░░░░░░░ │   ← 누르고 있는 동안 왕복하는 와인드업 미터
  └─────────────────────────┘      가운데 초록 구간에서 떼면 releaseAccuracy 최대
        누르고 → 조준하고 → 뗀다
```

- **누른다**: 와인드업 미터가 좌우로 왕복 시작. 미터 속도는 피로가 높을수록 빨라진다.
- **끈다**: 조준 크로스헤어가 고른 칸 안에서 움직인다. 손을 뗄 때 칸 중심에 가까울수록
  `aimAccuracy`가 높다.
- **뗀다**: 미터 위치로 `releaseAccuracy`가 정해지고 투구가 실행된다.

### 3.4 접근성 — 배제하지 않기

**"자동 릴리스" 설정을 둔다.** 켜면 항상 중립 500/500으로 던진다. 즉 오늘과 같다.

이건 선택 사항이 아니라 필수다. VoiceOver, 스위치 컨트롤, 손 떨림이 있는 사용자에게
타이밍 제스처는 게임 자체를 잠근다. 기본값은 수동이되, 설정 첫 화면에 노출한다.

`accessibilityReduceMotion`이 켜져 있으면 미터 왕복 속도를 낮춘다.

## 4. H — 고교 커리어 iOS 이식

### 4.1 왜 가장 ROI가 높은가

`HighSchoolCareer.swift` 2,042줄이 **이미 완성돼 데스크톱에서 돌아간다.** 만들 것은 화면뿐이다.

그리고 이 모드는 게임 제목 그 자체다 — "야구 못하면 또 환생함". 고교 3년을 보내고 드래프트를
받고, 실패하면 기억 카드를 안고 다시 태어난다. **프로 커리어의 밋밋한 주간 루프 앞에 놓일
서사가 여기 있다.**

### 4.2 단계

`HighSchoolCareerPhase` 10단계를 그대로 화면에 대응시킨다.

| 단계 | 화면 | 코어 호출 |
|---|---|---|
| `prologue` | 환생 도입. 카르마·계승 기억 표시 | `completePrologue` |
| `schoolSelection` | 학교 4곳 카드(철학·감독·포수·강점·대가) | `chooseSchool` |
| `training` | 분야 6종 × 강도 3단 + **오늘의 기회** | `commitTraining` |
| `relationship` | 이벤트 카드 + 대응 3택(듣기/설명/맞서기) | `resolveRelationship` |
| `importantGame` | **PitchSession 재사용** — 시나리오에서 상황 구성 | `recordImportantGame` |
| `awakening` | 각성 3택 (효과 문구 포함) | `chooseAwakening` |
| `chapterReview` | 챕터 마무리 · 성장 요약 | `advanceChapter` |
| `draft` | 지명 결과 발표 | `resolveDraft` |
| `legacy` | **기억 카드 선택 → 다음 생** | `selectLegacy` |
| `completed` | 프로 진출 또는 환생 분기 | — |

### 4.3 중요 경기 재사용

`PitchSession`을 고교에서도 쓴다. 현재는 `ProCareerSnapshot`만 받으므로 **입력을 추상화**한다.

```swift
struct PitchScenario {          // 프로·고교 공통 입력
    let pitcher, lineup, scouting, defense, park
    let inning, outs, runners, leverage
    let headline, detail
}
```

고교는 `ImportantGameScenarioContent`(이닝·아웃·주자·레버리지·서사를 이미 다 갖고 있다)와
`RivalSnapshot`(타격 수치까지 갖고 있다)에서 시나리오를 만든다. 프로보다 오히려 정보가 많다.

### 4.4 드래프트 → 프로 연결

지금 `CareerBootstrap.draftResult`는 시드에서 지명을 **날조**한다. 고교 커리어가 붙으면
`HighSchoolCareerSnapshot.draftResult`가 진짜 결과를 준다. 날조 경로는 "프로부터 바로
시작" 옵션으로 남긴다(고교 3년을 건너뛰고 싶은 사용자를 위해).

## 5. R — 리텐션 레이어

### 5.1 환생 루프 — 게임의 제목이 곧 리텐션 구조다

코어에 이미 있다. iOS에만 없다.

```
고교 커리어 → 드래프트 → legacy 단계
   → 기억 카드 N장 선택 (memorySlots만큼)
   → lifeNumber + 1, inheritedMemories, 카르마 선택
   → 새 고교 커리어 (더 강한 시작, 더 어려운 조건)
```

`KarmaID` 6종은 각각 보상 배율(150‰~350‰)이 붙은 **자발적 핸디캡**이다. 이건 로그라이트의
검증된 재접속 장치다. 화면만 붙이면 된다.

### 5.2 Game Center

| 종류 | 항목 |
|---|---|
| 리더보드 | 명예의 전당 점수(`hallOfFameScore` — **이미 계산되는데 아무 데도 안 쓰인다**) |
| 리더보드 | 통산 탈삼진, 최고 회차(lifeNumber) |
| 업적 | 첫 지명 / 1군 데뷔 / 시즌 100탈삼진 / 무실점 중요 경기 / 3회차 도달 / 카르마 클리어 등 |

구현 원칙:

- **Game Center 미인증에서도 앱이 정상 동작한다.** 인증 실패는 조용히 무시한다.
- **업적을 로컬에도 미러링한다.** App Store Connect 설정 전이나 오프라인에서도 앱 안에서
  달성 목록이 보여야 한다. 이게 실제 재접속을 만드는 부분이고, GC는 자랑 채널일 뿐이다.
- 제출 로직은 순수 함수로 분리해 테스트한다(GC 자체는 시뮬레이터에서 테스트 불가).

## 6. 작업 순서와 근거

```
S(사운드) → D(손맛) → H(고교 이식) → R(리텐션)
```

- **S 먼저**: 다른 셋과 의존이 없고, 이후 모든 화면이 소리를 갖고 태어난다. 나중에 하면
  화면마다 돌아가서 큐를 심어야 한다.
- **D 두 번째**: 코어 변경이라 파급이 크다. 고교 이식 전에 끝내야 고교 중요 경기가 처음부터
  새 조작으로 만들어진다.
- **H 세 번째**: 가장 크다. S와 D가 끝난 뒤여야 새 화면들이 소리와 손맛을 갖고 나온다.
- **R 마지막**: 환생 루프는 고교 커리어의 `legacy` 단계에 붙으므로 H에 의존한다.

## 6.1 구현 결과

| 축 | 상태 | 산출물 |
|---|---|---|
| S 사운드 | 완료 | `GameAudio.swift`(AVAudioEngine 절차 합성), `GameAudioCueMapping.swift`, 설정 토글 |
| D 손맛 | 완료 | 코어 `PitchDelivery` + `submitPitch(_:delivery:)`, `DeliveryControl.swift`, 자동 릴리스 |
| H 고교 이식 | 완료 | `HighSchoolCareerStore`·`HighSchoolCareerView`·`HighSchoolSetupView`·`HighSchoolPresentation`, `PitchScenario`로 승부 화면 공유 |
| R 리텐션 | 완료 | 환생 루프(계승·카르마), `Achievements.swift`·`AchievementStore`·`AchievementsView` |

탭 구조가 **고교 / 프로 / 기록 / 설정** 넷으로 바뀌었다. 프로 탭은 고교 드래프트를 통과해야
열리고, 고교를 건너뛰고 싶은 사용자를 위한 우회로를 그 화면 안에 둔다.

### 화면 언어

카드 언어는 **A안(눈썹 + 헤어라인)**으로 확정했다. 규칙과 근거는 DOC-19 §7에 있다.
요약하면 **의미색이 붙은 것만 면을 갖고, 중립 정보는 타이포와 괘선으로만 선다.** 상태 변화는
드물게 일어나므로 이 규칙 하나로 "강조는 화면당 한 곳"이 저절로 지켜진다.

함께 바로잡은 것:

- **라이트 모드로 렌더되던 문제.** 디자인 시스템은 `color-scheme: dark`이고 라이트 팔레트가
  없는데, iOS 셸이 `adaptive(light:dark:)`로 토큰을 정의해 흰 앱이 됐다. 다크 고정으로 바꾸고
  검사에서 명암 분기를 금지했다.
- **좌측 강조 레일의 남용.** 데스크톱은 GameCast의 ABS 판정 한 곳에만 쓰는데 모든 카드가 반복했다.
- **스플래시 잘림.** 로고를 760px 단일 배율로 넣어 760pt로 렌더됐다(화면 폭 393pt).
  1x/2x/3x로 나눠 240pt 표시로 잡고, 런치 배경 색세트의 라이트 값도 제거했다.
- **포수 요구 코스 아이콘.** 손가락 기호가 "여기를 눌러라"로 읽혀 표적(`target`)과 범례로 바꿨다.

### 구현 중 발견해 고친 결함

- **Swift 6.3 outlined destroy 오버릴리즈.** `PitchDelivery`를 넣자 전혀 무관한
  `HighSchoolCareerSnapshot`의 컴파일러 생성 destroy에서 전체 스위트가 SIGSEGV로 죽었다.
  개별 테스트는 모두 통과하고 스위트 전체에서만 터진다. 이 패키지가 `CareerScheduleSnapshot`에서
  한 번 겪은 것과 같은 결함이라, 같은 처방(`final class` 박싱 + 명시 `==`)으로 고쳤다.
  덤으로 `delivery`를 `SubmitPitchParams`에 넣지 않고 별도 인자로 받아 RPC 페이로드 형태도 지켰다.
- **오디오 렌더 콜백의 액터 격리.** `AVAudioSourceNode`의 블록을 `@MainActor` 클래스 안에서
  만들면 Swift가 메인 액터 검사를 끼워 넣고, 오디오 스레드에서 `dispatch_assert_queue`가
  실패해 앱이 SIGTRAP으로 죽었다. `nonisolated` 팩토리로 분리했다.
- **기억 카드 장수 미검증.** 코어는 정확히 `memorySlots`장을 요구하는데 화면이 부족한 채로
  확정을 허용해 커리어가 오류 상태로 빠졌다. 버튼을 비활성화하고 남은 장수를 안내한다.
- **테스트 간 설정 누수.** `-uiTestAutoRelease`가 UserDefaults에 남아 다음 테스트의 조작
  경로를 바꿨다. 리셋 인자가 설정도 함께 되돌린다.

## 7. 검증 기준

| 기준 | 방법 |
|---|---|
| 코어 골든 픽스처가 깨지지 않는다 | `swift test --package-path packages/simulation-core` |
| `delivery == nil`이 기존과 동일하다 | 같은 입력으로 delivery 유무 비교 테스트 |
| 중립 입력(500/500)이 nil과 동일하다 | 동일성 테스트 |
| 조작이 결과에 영향을 준다 | 정확한 릴리스 vs 빗나간 릴리스의 executionQuality 차이 |
| 자동 릴리스가 손맛 없이도 완주된다 | UI 스모크 테스트를 자동 릴리스로 1회 |
| 고교 커리어를 끝까지 갈 수 있다 | 프롤로그→드래프트→환생 UI 스모크 |
| 오디오가 사용자 음악을 끊지 않는다 | `.ambient` + `.mixWithOthers` 계약 검사 |
| 업적 판정이 정확하다 | 순수 함수 단위 테스트 |
