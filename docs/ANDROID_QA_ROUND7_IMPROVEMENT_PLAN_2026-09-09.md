## 1. W-01 — 보상 조건·표시·명령을 같은 규칙으로 통일

### 확인한 원인

`buildP024_WEEKLY`는 `tasks.any { it.completed }`로 버튼을 활성화하지만, `HighSchoolPhase4Kernel.claimWeeklyReward`는 완료 과제 2개 이상을 요구한다. 추가로 `RecordsSegments`의 주간 노트 보상 표시도 `any`를 사용하고 설명은 ‘과제를 하나라도 채우면 받을 수 있다’고 되어 있다. 버튼 한 줄만 수정하면 배지와 설명이 계속 잘못된다.

### 변경 계획

- `HighSchoolWeeklyRules`에 최소 완료 수와 보상 자격 판정을 모은다. 완료 수뿐 아니라 이미 수령했는지와 챌린지 제한도 포함한다. 커널의 기존 거부 코드(`weekly.incomplete`, `weekly.already_claimed`, `weekly.challenge_locked`)는 유지한다.
- 버튼, 보상 표시, 본문 설명, 버튼의 접근성 설명, 커널 수령 판정이 같은 규칙을 참조하도록 한다. ‘주간 과제 2개 이상 완료하면 받을 수 있어요’처럼 실제 규칙을 설명한다.
- 완료 0/1개, 수령 완료, 챌린지 제한 상태에서는 클릭 가능한 보상 명령을 노출하지 않는다. 이유는 본문에서도 읽을 수 있게 한다.
- 캐시된 화면/명령은 실행 직전 현재 상태로 검증한다. 연속 탭이나 주차 변경·복원으로 조건이 달라져도 보상을 중복 지급하지 않는다.

### 완료 기준

| 상태 | 버튼/표시 | 명령 결과 |
| --- | --- | --- |
| 완료 0개·1개 | 비활성, 보상 가능 표시 없음, 부족 조건 안내 | 직접 호출해도 거부, 상태·보상 불변 |
| 완료 2개·3개 / 미수령 | 활성, 실제 조건과 같은 설명 | 기존 규칙대로 1회 지급 |

## 2. W-02 — 원인 분류와 사용자 안내를 공통으로 고치기

### 확인한 원인

`GameActionFailurePresentation.message`는 일부 stale revision/투구 오류만 구분한 뒤 나머지를 저장 실패로 처리한다. 같은 actionId로 실패하면 원인과 무관하게 저장 공간 안내로 바뀐다. `MainActivity`도 실패 종류와 관계없이 `failingActionId`를 기록한다.

또한 `reconcilePersistedRevision()` 호출의 `isSuccess`를 `refreshed`로 넘긴다. 읽기 호출 성공, durable 파일 확인, 실제 revision 변경은 서로 다른 사실이므로 구분해야 한다.

### 변경 계획

공통 실패 분류 결과에 종류·표시 키·허용할 복구 동작·저장 실패 반복 집계 여부를 둔다. 단순 메시지 문자열 검색이나 예외 최상위 타입 하나만으로 결정하지 않고 typed 저장 오류 코드와 원인 체인을 함께 본다. 진단용 suppressed context는 실패 원인 자체로 분류하지 않는다.

| 분류 | 사용자 안내/동작 | 저장 실패 반복 집계 |
| --- | --- | --- |
| `weekly.incomplete` | 과제 2개 이상 필요, 현재 부족 조건 안내 | 제외 |
| 이미 수령/챌린지/커리어 범위 제한 등 알려진 규칙 거부 | 해당 이유를 번역된 문구로 안내 | 제외 |
| stale revision/충돌 | 실제 상태 재확인 결과로 화면을 갱신하고 유효한 행동만 다시 제공 | 제외 |
| 명시적인 공간 부족 원인 | 저장 공간 확인 안내 | 공간 부족으로 별도 집계 |
| 일반 I/O 실패 | 저장 작업 실패와 안전한 복귀/재확인 안내 | 같은 저장 원인·행동일 때만 집계 |
| 검증/직렬화/마이그레이션/쓰기 금지 | 각각의 문제에 맞는 안내, 원본 보존 | 공간 부족으로 분류하지 않음 |
| 원인 미확정 | 진행을 완료하지 못했다는 안내와 진단 ID | 저장 공간 추정 금지 |

`GameCommandException`이라는 이유만으로 전부 정상적인 규칙 거부라고 간주하지도 않는다. 알려진 도메인 거부 코드는 사용자 문구로 매핑하고, 알 수 없는 코드는 진단 대상으로 남긴다. 원시 `weekly.incomplete`나 스택을 사용자에게 그대로 표시하지 않는다.

`SaveRepositoryException`에도 IO_FAILED 외에 검증·버전·충돌·쓰기 금지 코드가 있으므로 모두 저장 공간 문제로 묶지 않는다. **일반 IOException이나 반복 횟수만으로 공간 부족이라고 말하지 않는다.** 플랫폼에서 확실한 공간 부족 근거를 얻지 못하면 일반 I/O 안내를 사용한다.

반복 상태는 actionId만이 아니라 실패 종류/원인에 연결한다. 성공하거나 상태가 달라졌을 때 해제하고, 규칙 거부는 반복해도 저장 오류로 승격하지 않는다. 6차의 명령 ID·원인 로그와 투구 전용 durable 결과 복구는 유지한다. 자동으로 보상 명령을 재실행하지 않는다.

### 완료 기준

- `weekly.incomplete`를 1회·3회·여러 회 주입해도 ‘저장 실패’, ‘같은 버튼을 다시’, ‘저장 공간’ 안내가 나오지 않는다.
- 이미 수령/챌린지/커리어 제한/stale revision과 실제 I/O·검증 실패의 분류를 교차 검사한다. 규칙 거부 뒤 I/O 실패, 성공 뒤 다시 실패하는 순서도 포함한다.
- 규칙 거부 전후 저장 revision·커리어·보상은 불변이다.
- 읽기만 성공한 상태를 실제 화면 갱신이나 durable 확인으로 과장하지 않는다.
- 보상 버튼의 오류 화면을 native 저장 경로와 실제 UI에서 확인하고 로그의 원인과 사용자 설명이 일치한다.

## 3. W-03 — 프로에서 고교 주간 노트 비노출

이번 수정에서는 **프로용 새 주간 보상 시스템을 만들지 않고, 프로 진행·은퇴 화면에서 고교 주간 노트를 숨긴다.** 프로에는 현재 달성할 수 있는 주간 계획·시즌 목표·승격 안내가 이미 있으므로, 별도 과제/재화 밸런스를 이번 결함 수정에 추가하지 않는다.

화면만 숨기지 않고 다음을 함께 적용한다.

- 주간 노트의 활성 커리어 소유권 정책을 공통으로 둔다. 고교 데이터가 세이브에 남아 있다는 사실만으로 주간 노트를 활성화하지 않는다.
- 기록 탭 진입 칩, 보상 표시, 화면 도달 가능 여부, 저장된 선택 화면 복원 경로에 적용한다. 숨긴 칩의 빈자리는 남기지 않는다.
- 프로에서 캐시된 P-024 화면을 복원하면 유효한 기록/프로 화면으로 이동한다.
- aggregate 명령 처리에서도 프로 커리어에서 고교 주간 보상을 청구하는 요청을 거부한다. native bridge와 일반 reducer가 같은 정책을 사용하게 한다. 과거 화면의 captured payload로 우회할 수 없어야 한다.
- 고교·환생 과정의 과제는 실제 수행 가능한 단계에서 계속 사용할 수 있게 한다. 프로→새 고교 커리어 진입 때의 재노출도 확인한다.

기존 고교 도장·수령 이력·야구혼을 삭제하거나 잘못 지급됐다고 추정해 회수하지 않는다. 단순히 프로 문구로 이름만 바꾸고 고교 명령을 계속 보내는 방식도 사용하지 않는다.

**완료:** 고교 진행, 프로 직접 시작, 고교 연계 프로 3시즌, 프로 은퇴, 새 고교 커리어에서 노출/명령 범위가 일치한다. 특히 보고서의 연계 프로 세이브에서 고교 주간 과제와 보상 요청이 사라지고 프로·고교 기록은 유지된다.

## 4. W-04 — 정책·문의 링크의 Custom Tabs 적용

결함 수정과 분리된 사용성 보강이다. 현재 두 링크는 `uri.openUri`를 사용한다. 공용 링크 열기 도우미로 옮겨 Custom Tabs를 우선 사용하고, 미지원 환경에서는 외부 브라우저와 열기 실패 안내·URL 복사 경로를 제공한다. 새 의존성이 필요하면 기존 AndroidX/SDK와 호환되는 버전을 고정한다.

**Custom Tabs는 설치된 브라우저의 기능**이다. 지원 브라우저가 없으면 기본 브라우저로 돌아가므로, 도입만으로 모든 기기의 브라우저 첫 실행 화면을 피하거나 정책 본문 도달을 보장한다고 표현하지 않는다. [Chrome 공식 시작 가이드](https://developer.chrome.com/docs/android/custom-tabs/guide-get-started), [Android 공식 개요](https://developer.android.com/develop/ui/views/layout/webapps/overview-of-android-custom-tabs)

검증은 정상 설정된 브라우저, 브라우저 미설정/첫 실행, Custom Tabs 미지원 또는 브라우저 없음, 네트워크 실패를 나눠 수행한다. URL intent를 보냈다는 것과 개인정보/문의 본문이 실제로 열린 것을 구분하고, 앱 복귀 시 진행이 보존되는지 확인한다. 현재 보고서의 HTTP 200 결과는 보고서 근거이며 이번 계획 작성에서 다시 네트워크 측정한 값은 아니다.

첫 실행 환경에서 본문에 도달하지 못하면 Custom Tabs 적용만으로 해당 검증을 통과 처리하지 않는다. 오류/대체 경로까지 기록한 뒤 추가 앱 내 문서 표시가 필요한지 판단한다. W-04를 구현했다고 Play 심사 통과를 보장하지 않는다.

## 5. 검증·배포 준비와 완료 보고

실행 순서: **W-01과 W-03의 공통 정책 → W-02 공통 오류 분류 → 실제 주간 보상 UI 재검증 → W-04 링크 보강 → 가능한 실기기·서명 RC 검증**. 장비·서명 설정 존재 여부는 착수 때 먼저 확인한다.

7차 보고서 기준으로 실기기와 키스토어 설정이 없다. 실제 연결 상태를 다시 확인하고, 장비가 준비되면 주간 보상·복원된 화면·정책 링크·기존 슬라이더 투구를 검증한다. 서명 RC는 필수 설정이 갖춰졌을 때 실제 release의 업데이트 설치와 같은 여정을 확인한다. QA debug를 RC로 대체하지 않고 스토어 업로드·출시는 이 계획에 포함하지 않는다. TalkBack은 이번 범위에서 계속 제외한다.

변경 문구는 한국어·영어·일본어로 제공하고, 문구 게이트와 가상 야구 콘텐츠 규칙을 검사한다. 기존 세이브는 초기화 없이 업데이트하고 커리어·기록·도장 보존을 비교한다. 테스트용 초기화/실패 주입은 분리된 QA 설치에서만 수행한다.
