# Android 끊김 원인 검토와 최적화 제안

2026-09-06. 이번 작업은 진단·제안이다. 게임 코드와 사용자 진행은 변경하지 않았다.

## 확인 범위

실기기 Galaxy A53의 현재 전면 화면은 MainActivity였다. gfxinfo의 누적 표본은 4프레임(지연 3프레임)뿐으로, 시작 화면의 비용이 섞여 있다. 이를 ‘플레이의 75%가 끊긴다’고 해석할 수 없다. 현재 thermal status는 0이며 측정 시 발열 제한은 보고되지 않았다. 끊김의 최종 주원인은 구간별 트레이스로 확인해야 한다.

## 우선순위

1. **매 프레임 재실행되는 화면 계산 분리.** PitchActivity에서 애니메이션 진행률을 읽는 범위에 PitchHudProjection.model 호출이 포함된다. 해당 모델은 단순 텍스트 조합이 아니라 투구 준비/추천 계산까지 호출한다. 애니메이션 상태는 공의 그리기 단계에서만 읽고, HUD·추천·점수판은 해당 게임 상태가 바뀔 때만 계산해야 한다.
2. **궤적을 공마다 한 번 계산.** PitchDramaView의 Canvas에서 65개 궤적 점을 다시 계산한다. 각 점은 원본 점 검색·tanh 계산을 수행하며, 표시 구간을 만들면서 map/take로 목록을 추가 생성한다. request별 점·경로를 캐시하고 매 프레임에는 진행률과 공 위치만 보간한다. 최근 궤적 개선에서 추가된 반복 작업이므로 우선 정리할 가치가 높다. 실제 소요 시간은 아직 측정하지 않았다.
3. **심박 합성·기기 호출을 렌더 루프 밖으로 이동.** 메인 화면의 LaunchedEffect에서 44.1kHz 심박 PCM을 생성해 AudioTrack에 전달한다. 동일 강도/패턴의 PCM을 미리 만들거나 백그라운드에서 준비한다. 진동 설정·지원 여부도 매 틱 재조회하지 않고 복귀/설정 변경 시 갱신한다. 진동과 소리를 제거하지 않고 예약 타이밍을 유지한다.
4. **저장→다음 공 준비 지연을 별도 측정.** 저장은 이미 IO 경로다. 무조건 저장을 생략하거나 메인 스레드로 옮기는 방식은 부적절하다. 손을 뗀 순간, 저장 완료, 공 재생 시작, 다음 입력 준비 완료를 나눠 기록하고, 다음 공 준비 중 중복 HUD/재생 리소스 생성을 줄인다.
5. **성능 빌드와 주사율 비교.** 현재 테스트 앱은 Debug이며 release도 minify=false다. Debug 수치를 출시 성능으로 단정하지 않는다. 승인된 production 서명 게이트와 분리된 로컬 성능 검사 빌드에서 최적화 전후를 비교하고, A53의 60Hz/120Hz 양쪽에서 확인한다.

## 검증 계획

사용자 기록과 분리된 QA 앱에서 같은 저장·구종·입력과 기기 상태를 사용한다. 최초 실행은 따로 측정하고, 준비 이후 슬라이더 유지/릴리스/공 비행/판정/다음 공 전환을 각각 측정한다. Perfetto FrameTimeline·메인 스레드·RenderThread·GC·IO를 함께 보면 CPU 재계산과 GPU/업로드 비용을 구분할 수 있다.

- 60Hz는 16.7ms, 120Hz는 8.3ms 프레임 예산을 기준으로 p50/p95/p99와 놓친 프레임 비율을 기록한다.
- 50ms 이상 멈춤과 손을 뗀 뒤 첫 움직임까지의 지연을 별도 기록한다.
- 짧은 1회 성공이 아니라 같은 조건의 반복 투구·연속 실행에서도 개선이 유지되는지 확인한다.
- 구종별 궤적·도착점·판정·저장·햅틱 타이밍과 기본 수동 조작이 유지되어야 한다.

첫 적용 묶음은 1·2번이 적절하다. 이 두 항목은 게임의 재미 요소를 바꾸지 않고 렌더링 중 불필요한 일을 줄인다. 효과를 측정한 뒤 3·4번으로 이어간다. 현재 근거만으로 그래픽 품질 저하나 무조건 60Hz 고정은 권하지 않는다.
